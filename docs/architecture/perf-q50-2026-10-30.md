# Q50 perf baseline (2026-10-30)

Status: harness built and baseline measured on the `dev` box (Linux, 16 cores, no display, no audio device), branch `q50-harness` from `ov-1028`. Nothing is fixed yet; this is step 1 of the Q50 fleet. Earlier work this builds on: `performance-2026-10.md` (Q20 startup, Q23 track load, scroll, search).

**Read every number with the load average next to it.** The box ran at load 42-75 on 16 cores during all runs (other workers building and analysing). CPU-bound numbers (analysis, frontend boot, sorts) move up to about ±40% between runs; structural ones (payload bytes, decode start, cached reads, call counts) do not. Ranges below are min-max over the runs listed under "Runs".

## The command

```bash
scripts/perf.sh          # or: cd app && npm run perf
```

One command, about 12 minutes on a loaded box (first run also generates the 10k library, ~15 min). It prints a table and writes one JSON report to `benchmark/results/q50/perf-<stamp>.json` (gitignored); raw per-step output stays in `~/.cache/q50-perf/raw-<stamp>/`.

| Step | Tool | What it measures |
|---|---|---|
| startup backend | `bench_startup run` (release) | `load_state` on a generated 10k-track library: track query, `build_track_infos`, playlists, JSON. Once after evicting the library's page cache (`posix_fadvise DONTNEED`, no root needed), then 3 warm runs (median). |
| track load backend | `bench_startup load`, `bench_startup audio` | `get_analysis_data` (60 tracks, median/p95); symphonia probe, first packet, seek-to-middle decode on 12 real files; `waveform_detail::detail_bytes` cold (empty cache) and cached. |
| playback engine | `cargo test --release latency_load_and_seek_to_first_audio` | `PlaybackEngine` load and seek to first audible buffer with the fake output backend (existing test). |
| import | `bench_startup import` | 1000 symlinks to real dataset files (992 readable): survey, scan (lofty), `plan_for_library`, commit (exists check + `add_tracks`). Into an empty library with cold and warm page cache, and into the 10k library. |
| analysis | `bench_analysis --profile 3`, then `bench_analysis` | Per-stage ms from `Analysis::ms` (decode, resample, mel, predict = ONNX, fit, mp3, key, waveform/bands) plus `to_app_result` and the library write, one track at a time with all threads; then throughput of 6 tracks through `run_track_analysis` (the app path, staged). |
| frontend | `app/smoke/perf-q50.spec.ts`, `perf10k.spec.ts`, `perf-bulk-analysis.spec.ts` | Production build + smoke Tauri mock at 10k tracks: cold (fresh browser context) and warm (reload) boot to first row and interactive; track load to overview painted and to detail series; expand to detail drawn; import UI from click to rows; steady-state UI (scroll, search, sort, select, playlist, palette); UI while bulk analysis runs. |

Knobs: `FF_PERF_TRACKS`, `FF_PERF_IMPORT`, `FF_PERF_ANALYSIS`, `FF_PERF_PROFILE_TRACKS`, `FF_PERF_SKIP=startup,load,import,analysis,playback,frontend`, `FF_PERF_AUDIO` (dataset root, default the main checkout's `benchmark/datasets`), `FF_PERF_DIR`, `FF_SMOKE_PORT`. Every bench subcommand also prints a `PERF {json}` line, so each step runs alone.

### What the frontend numbers are and are not

- The mock answers in-page (no IPC, no WebKit). Startup passes the 10k payload through `addInitScript`, so its parse lands in boot like the real IPC JSON would, but the cost is Chromium's, not WKWebView's.
- The mock's `get_analysis_data` goes through a Playwright `exposeFunction` round trip and `get_waveform_detail` builds its buffer in the page: both cost ~0.5 s each and are **not app time**. The suite reports them separately and times the app from the moment the mock answers ("after backend answer"). Raw "track load to overview" (550-680 ms) is mostly mock.
- Real backend time for the same commands comes from the Rust rows.

## Worst offenders, ranked per path

Ranked by user-felt time: how long, how often it is hit, and whether it blocks the UI.

### Startup

1. **Frontend boot is one long main-thread block: 0.5-0.9 s longest task, ~0.9-1 s total blocking (cold).** CPU profile of boot at 10k (`FF_PERF_PROFILE=boot`, perf10k "boot profile"): 950 ms `(program)` (native: script parse, payload clone, layout), 540 ms in Svelte's first flush (`flush` → `process_fn`), of which `bind_element_size` effects 156 ms self (an element-size binding reads layout synchronously on mount), `mapTrackInfoToLocal` 71 ms, the search haystack warm-up (`trackHaystack`) 62 ms, `ensureFavoriteSlots` 29 ms; 215 ms GC. Next: split the first flush (rows first, warm-ups after first paint), find which `bind:clientWidth/Height` runs per row or per cell.
2. **Backend `build_track_infos`: 254-637 ms at 10k**, up to 2x with a cold page cache (it reads the PWAV section of 10k ANLZ files). Plus the track query (85-157 ms). Q20 already parallelised it; what is left is the file count. Options: keep the 400-byte preview / row bands in SQLite, or send previews lazily for visible rows.
3. **8.5 MB `load_state` JSON** (64-140 ms to serialise here; WKWebView parse on the Mac unmeasured). Shrinks with item 2's lazy previews.

### Track load

1. **Waveform detail the first time a track opens: 0.8-1.8 s median, up to 2.2 s p95** (`band_analysis::measure_detail`: one full single-threaded decode plus the 3-band meter, then a cache file). Selecting a row prefetches it for that row and the next two, so a double-click on an unselected row pays it in full. It decodes the same file that analysis already decoded and whose bands (`waveform::compute`) analysis already measured at a lower rate. Options: produce the detail series during analysis (same decode), or parallelise the meter.
2. **Expand to detail drawn: 110-149 ms** in the page (`bandsFromDetailBytes` on a 1.44 MB series plus the first zoom draw).
3. Overview painted 47-78 ms after the backend answers; backend answer 3-6 ms; decode start and first audio under 10 ms. **Not an offender**: the audio path is fast.

### Import (1k files)

1. **Scan with a cold page cache: 0.9-1.5 s** (lofty tag reads, one file after the other); warm 0.17-0.25 s. IO-bound; a parallel scan would overlap the reads.
2. **`add_tracks`: 0.43-0.63 s for 992 tracks**, almost all of `commit_import` (the exists check is 14-51 ms). Evidence: the import WAL grew to 25 MB for 992 tracks: the full-size embedded artwork is written as a blob per track inside the transaction. Options: store a downscaled thumbnail, or write artwork after commit.
3. **Plan into a 10k library: 256-366 ms** (`plan_for_library` loads every library track with `get_all_tracks` to build the duplicate index), grows with library size.
4. **UI: one 275-319 ms long task when 1k rows land in a 10k library** (worst frame ~330 ms).

### Analysis

1. **The ONNX beat model (`predict`) is 86-89% of every track** (12-22 s of 14-24 s per 2-minute track with 15 threads at load ~50). Everything else together is ~2 s. Any real throughput win is here: model threading/batching, smaller input (window/hop), or a quantised model; BPM/grid results must stay identical, so this needs a reference comparison.
2. **Staged analysis decodes and resamples every track twice.** `Pass::Fast` and `Pass::Grid` are two separate `analyze_controlled` calls, and each starts with `decode_mono` and a resample (`fourfour-analysis-rs/src/service.rs`, `analyze.rs`): ~1.2-1.6 s of decode + resample per extra pass. Keeping the decoded audio for the grid pass (or one pass that reports waveform/key early) removes it.
3. **Mel + resample + decode: ~1.8-2.6 s per 2-min track**, serial before the model.
4. Library write 52-62 ms and fit 45-57 ms per track: not offenders.

Throughput is 0.9-1.3 tracks/min here for 6 tracks; Q21 measured 2.36/min on 50 tracks with 8 workers on a quieter box (`docs/analysis/app-integration-2026-10.md`). The 6-track run is short on purpose (5-7 minutes); raise `FF_PERF_ANALYSIS` for a steadier figure.

### UI responsiveness

1. **Typing during the bulk fast pass: worst keystroke 0.67-2.4 s, palette up to 1.3 s; the main thread is busy ~0.7 s per second even with no input and no events** (`perf-bulk-analysis.spec.ts`, owned by the bulk-analysis worker). Idle (no analysis) is 0.8 s/s too while scrolling, so part of this is the headless renderer; worth a profile before blaming the app.
2. **Sort at 10k: 141-280 ms per click**; search clear up to 389 ms; opening a 2k playlist 165-302 ms. All are O(N) passes over Svelte-proxied tracks (Q20's remaining items).
3. Fling scroll p95 54-109 ms (row mount + mini-waveform draw).

## Track load results

Branch `q50-trackload` (from `ov-1028`). Target: the first detail waveform of a track.

**Cause.** `measure_detail` is one single-threaded pass: symphonia decode, then the `DetailMeter` (four biquads per sample plus the column extremes). On the 12 harness files at load 24 (release): decode 375-384 ms, meter 295-303 ms. In the app's dev build (`pioneer-test-ui/dev.sh` runs `cargo tauri build --debug`) the meter is unoptimised: `pioneer-usb-writer` had no `profile.dev` opt-level, so the meter took 1,565 ms instead of ~300 (5x), and the whole detail 2.6 s per 2-minute preview. The disk cache (512 MiB LRU in the app data folder, keyed by path, size and mtime) already survives restarts; only the first open of a track pays.

**Changes.**

1. `Cargo.toml`: `[profile.dev.package.pioneer-usb-writer] opt-level = 3` (like the symphonia and analysis crates). Rebuild cost: the writer crate only.
2. `band_analysis::decode_blocks_parallel`: a reader thread splits the packets into segments of 256 packets; up to 6 threads (cores - 1) decode a segment each with a fresh decoder that first decodes the 16 packets before it and drops them (MP3 bit reservoir, overlap-add and synthesis state); the meter consumes the segments in order on the calling thread while later ones decode. Read-ahead is bounded (2 x threads + 2 segments, ~50 MB for a stereo 44.1 kHz track). `measure_detail` uses it; the analysis paths (`decode_blocks`, `measure_waveforms`) are untouched.
3. Row press warms the detail: `createDetailPrefetcher().now(id)` on pointer-down in `TrackTable`, ahead of the 150 ms debounced select prefetch, so a double-click on an unselected row starts the decode 250-400 ms earlier.
4. For the analysis (follow-up, not wired): `band_analysis::measure_waveforms_and_detail` (one decode feeds both meters) and `waveform_detail::store_detail` (writes the cache entry).

**Equivalence.** `bench_startup detail <list>` compares, per file, the parallel decode with the single-threaded one sample by sample (f32 bits) and the detail bytes of old and new `measure_detail`: **identical on 67/67 files** (49 MP3, 12 WAV, 6 FLAC, every 20th file of the dataset list, previews and full tracks) and on the 12 harness files. Unit test: a 40 s WAV through 3 threads gives the same samples, detail and waveforms as one thread.

**Before / after** (back to back on the same box, median/p95):

| Build | Files | Before (one thread) | After | Load |
|---|---|---|---|---|
| release | 12 harness previews | 636 / 673 ms | 351 / 385 ms | 28 → 26 |
| release | 67 mixed (incl. full tracks) | 752 / 4,354 ms | 447 / 2,503 ms | 24 → 33 |
| dev (`dev.sh`), writer unoptimised → optimised | 12 harness previews | 2,622 / 3,312 ms | 456 / 555 ms | 21 → 23 |
| harness `bench_startup audio`, `detail_cold` | 12 | 844-1,820 ms (baseline runs, load 42-75) | 396 / 521 ms | 24 |

Cached reads stay 0.9-2.8 ms. The parallel decode leaves the meter as the floor: after the change the detail takes about the meter's time (~300 ms per 2-minute track, ~0.9 s for a 6-minute one on this box).

**Expand to detail (110-149 ms, 200-330 ms at load 49).** Profile (`FF_PERF_PROFILE=expand npx playwright test perf-q50 --grep expand`): 141 ms in Svelte's flush, of which 85 ms is `WaveformDisplay.setData` → `_paint` (`_renderZoom` 57 ms, `_renderBands`/`drawBandRange` 34 ms); `bandsFromDetailBytes` is already zero-copy. The time is in the design-system renderer (`prototyping/viewport/design-system/waveform-display.js`), outside this branch's scope.

**Follow-ups.**

- Analysis fills the cache: in `analysis_run.rs` swap `measure_waveforms(&bands_path)` for `measure_waveforms_and_detail` and `store_detail` into the app data `waveform-detail` folder; an analysed track then never decodes for its detail. Done on `q50-analysis` for the Python now lane; the Rust analysis path measures its waveform from the mono mix and has no detail meter, so its tracks still decode once for the detail.
- Meter in parallel (the remaining ~300 ms): needs `DetailMeter` to hand out raw peaks and extremes per segment (`pioneer-usb-writer/src/waveform/detail.rs`); segments start on 2400-column edges, run with an audio pre-roll, and are checked for identical columns on an overlap before they are joined.
- Cache size: 512 MiB holds ~100 six-minute tracks (5 MB each); a larger cap or a compressed file keeps more of a library warm.
- Expand: draw the zoom view once per frame after mount instead of in the mount flush (design system).

## Analysis results

Branch `q50-analysis` (worker q50-analysis, 2026-10-29). Benchmark set: 12 files picked like `perf.sh` does (every Nth of the dataset list): 7 Beatport previews (2 min, mp3) and 5 full tracks (5-7 min; mp3, wav at 44.1 and 48 kHz, flac), 44 min of audio. List in `~/.cache/q50-analysis/list12.txt`.

### Cause

The beat model runs in 30 s chunks, and each chunk ran on a thread that belonged to one track: a track got `threads_per_track` chunk workers, fixed when it started. With 12 tracks queued every grid pass started with 1 thread (15 threads / 12 jobs), so the batch ended with the 5 full tracks (11-15 chunks each) running one chunk at a time while 10 cores idled, and the first result waited for a whole track on one thread. The model's CPU cost did not change; the cores were idle.

### What changed

- `bt.rs`: one chunk executor per `BeatEngine`. Its threads (at least `max_threads`, set by `Analyzer::load`) take chunks of every running track in arrival order, each on a single-thread rten pool as before. A track whose chunks are all taken leaves its threads to the others. Pause and cancel work per track as before (a paused track's chunks are skipped, a cancelled track's are dropped). The threads start inside the first analysis call, so they inherit its lowered priority (`run_below_ui`); total model threads stay `max_threads` = cores - 1.
- `analysis_run.rs`: at most `max_threads / 3` (min 3) model jobs (grid or whole) in flight; fast passes are not limited. More model jobs only hold decoded audio while they wait for the shared threads.
- `analysis_run.rs` (Python now lane): waveform and detail come from one decode and the detail goes into the `waveform-detail` cache (`store_detail`).
- `bench_analysis --dump <file>` writes every result (app path: the stored `AnalysisResult`; `--profile`: beats, downbeats, key, waveform checksum and raw logits) for the equality check below.

### Before / after

| after B | 21.4 | 9.37 | 16 s | 77 s | 543 + 96 s | 6.66 GB |

Throughput 2.5-7.5 → 9.4-11.4 tracks/min, first result 36-120 s → 13-18 s, same CPU seconds. The job cap alone (executor runs D1/D2, interleaved): 11.5 / 8.3 tracks/min with the cap vs 10.2 / 8.9 without, peak RSS 6.2-6.5 vs 6.6-6.9 GB.

Per stage, one track at a time with 15 threads (`--profile 12`, medians, unchanged as expected): predict 6.5 → 6.6 s, mel 0.50 → 0.43 s, resample 0.50 → 0.40 s, decode 0.35 → 0.37 s, waveform 0.33 → 0.30 s, key 0.22 → 0.18 s, fit 27 → 21 ms, write 29 → 34 ms (load 14-27).

### Output equality

`~/.cache/q50-analysis/compare.py` on the dumps: 12 of 12 tracks identical in every run pair (A, B, E1, E2): stored BPM, key, beat grid (time, bar position, tempo), waveform preview and colour waveform. Profile dumps (before vs after, 12 tracks): raw beat and downbeat logits bit-identical (max difference 0), final beats, downbeats, BPM, key and waveform checksum identical. New test `tracks_sharing_the_chunk_threads_get_the_logits_they_get_alone_and_a_paused_one_waits` (needs weights, `--ignored`) checks the same on generated audio, plus pause and cancel.

### Evaluated, not changed

- **RSS (5-6.5 GB)**: held by the model's activations, about 0.4 GB per chunk running at once (rten allocates a fresh buffer pool for every run; 15 chunks in flight ≈ 6 GB). Decoded audio is minor (the job cap saves ~0.4 GB here, more on a library of full tracks). The executor runs 15 chunks at once also in a 12-track batch where 12 ran before, hence +0.8 GB on this set; a batch of ≥15 tracks reached 15 before too. Lower RSS means fewer chunks at once (slower) or another runtime.
- **sys time 15-19% of CPU** (17-22 M minor page faults per run, ~70 GB of zeroed pages): the same per-run buffer pool. glibc knobs (`MALLOC_MMAP_THRESHOLD_`, `MALLOC_MMAP_MAX_=0`) cut faults 24% and sys time 3 s of 95: not worth a Linux-only hack.
- **Intra-op threads per chunk** (rten pool of 3 per chunk): logits bit-identical, but predict only 18% faster at 3x the threads (5.7 → 4.7 s for 3 previews, 6 workers). Could shorten the now lane of one short track; not done.
- **Fewer chunks / smaller windows**: the last chunk overlaps the one before it by up to a whole chunk, but its frames win only at the end and depend on the whole window; dropping it changes the logits. Not done.
- **Decode once in staged mode**: the grid pass repeats decode and waveform (~0.55 CPU-s per audio minute, about 4% of a track's CPU). Keeping the decoded audio from the fast pass costs ~0.5 GB for this set and helps only tracks whose grid pass follows soon (fast passes of the whole queue run first). Not done; below this box's noise.
- **Batching chunks**: chunks are 1500 frames, already a large GEMM M dimension; not tried.
- **Proposal (new dependency, Merlin's call)**: rten 0.24 → 0.27 (newer releases exist; may reuse buffers across runs or speed attention), or `ort` (onnxruntime; arena allocator, fused attention, likely lower RSS and fewer page faults). Both need a reference comparison of the logits, since another runtime will not be bit-identical.

## Startup results

Branch `q50-startup` (from `ov-1028`). Target: first rows and an interactive app at 10k tracks, no boot task over ~100 ms.

**Causes (measured).**

1. Backend: `build_track_infos` no longer read ANLZ files (the row preview is in `analyses.row_preview` since schema v4), but it opened **two sidecar files per track** (`imported.json`, `edits.json`, via `imported_meta` and `effective_rating`): 20k failed opens one after the other, ~70 ms warm. It also ran four queries (track rows with flags, row previews, incomplete ids, the rows again inside) and built maps from them.
2. Frontend: the `load_state` answer ran as **one task**: `mapTrackInfoToLocal` decoded every track's base64 row preview (`decodeBandPreview` 167 ms incl. `atob`, 10k tracks) and built 10k objects with accessor properties (each accessor pair makes every object pay: ~35-55 ms for 10k in V8 whatever the count), wrapped them, ran `syncTrackFavoriteFields` (10k proxy writes), then the first flush mounted every pool row, overscan included (~55 rows, 2-4 ms each).
3. Harness: the smoke mock answered `invoke` in a microtask, so the shell mount and the `load_state` work fell into one task (the 0.5-0.9 s "longest task"). The real IPC answers in a task of its own. The perf harness now does the same (`FF_PERF_IPC_TASK=0` restores the old behaviour); both are reported below.
4. Not a cause: JSON parse. V8 parses a 9 MB `load_state` with previews in 34-54 ms and without them in 25-50 ms (the base64 strings are cheap to parse), so a binary or columnar encoding is not worth it.

**Changes.**

1. `pioneer-library`: `get_track_list_rows` (one query: list fields, artwork flag, analysis stages, row preview) and `TrackLabelsReader` (rating and colour from the sidecars, the ANLZ folder listed once, files read on all cores). `build_track_infos` runs the reader on a thread while SQLite answers. No schema change. `bench_startup run` reports `labels_ms`.
2. `library.svelte.ts`: the embedded row preview stays as its wire string (`bandsWire`) and is decoded, through a 512-entry cache, only when a row's `bands` is drawn; re-analysis clears it with `bandsPreview`/`preview`. The 10k tracks are mapped in 2,500-track chunks (a task each). FAV comes from the loaded playlists at map time; `ensureFavoriteSlots` only adds or drops empty playlists, so it no longer re-syncs every track, and `syncTrackFavoriteFields` writes only changed values.
3. `TrackTable.svelte`: the first rows mount without overscan; the overscan rows mount one frame later (`requestAnimationFrame` then a task). Same rows on screen.
4. Harness: `FF_PERF_Q50_ONLY=startup` (boot only), `FF_PERF_IPC_TASK`, `FF_PERF_PROFILE=boot-trace` (Chromium trace plus CPU profile of boot, `FF_PERF_PROFILE_OUT`), `FF_PERF_PROFILE_OUT` for the `perf10k` profiles.

The cold longest task left (200-250 ms) is the shell mount before `load_state` answers: module evaluation and `App` mount ~115 ms (header 36 ms of which 29 ms is the first `toLocaleString` initialising ICU, sidebar 31, player 17), then the first layout of the page ~85 ms forced by a `bind:clientHeight`. In the app this runs while the backend builds the answer (~110-130 ms), so it mostly overlaps.

**Not changed (measured).** Sort at 10k: the comparison itself is ~12 ms (an index sort without the keyed objects was no faster in V8); the rest is reading the key through the track proxies and re-rendering ~55 design-system `TrackRow`s, plus `persist()` writing the table layout to `localStorage` on every click (~5-12 ms). Search clear and opening a 2k playlist are row re-renders too. Faster row updates need `TrackRow` (`prototyping/viewport/design-system`), outside this branch.

**Follow-ups.**

- Real artwork makes the `has_artwork` join read one artwork leaf page per track (the image blob starts in the row): ~40 MB of pages cold for 10k tracks with covers. An index `CREATE INDEX artwork_track ON artwork(track_id)` (or a `has_artwork` column) would make it an index-only scan. Schema change, not done; the bench library has 64-byte covers, so it was not measurable here.
- The shell mount: mount the hidden overlays (settings sheet, dialogs, palette) on first use, and give the header count a formatter that does not wake ICU on boot.
- The search index's last idle step (`haystacksFor`, ~45 ms) ignores the idle deadline; chunk it like the warm-up before it.
- Measure on the Mac: IPC transfer and WKWebView parse of the 8.5 MB answer are not in these numbers.

## Analysis results 2

Branch `q50-analysis2` (worker q50-analysis2, 2026-10-29), same 12-track set and `bench_analysis` app path; scripts and dumps in `~/.cache/q50-analysis2/`. Baseline = `ov-1028` (8716bd1).

### Memory budget for the beat model (8 GB Mac)

rten has no way to reuse a buffer pool across runs: `Graph::run` builds `BufferPool::new()` on every call, in 0.24 and in 0.27, and `run_subgraph` (which takes a pool) is not reachable from `Model`. So the activations stay ~0.4 GB per chunk in flight, and the lever is how many chunks run at once.

- `service.rs`: `chunk_slots` = `(min(total RAM / 4, available / 2) - 600 MB) / 400 MB`, at least 1, at most `max_threads`. `Analyzer::load` gives the engine that many shared chunk threads. 8 GB Mac: 3; 16 GB: 8; dev (64 GB): 15 (unchanged).
- `bt.rs`: the shared count is now a cap; the now lane asking for all threads no longer adds threads beyond it.
- `FOURFOUR_ANALYSIS_MEMORY_MB` simulates a smaller machine (total = that, available = half of it, as on macOS); it also feeds `plan_pool`, so jobs in flight (decoded audio) shrink with it.

| Run | Load at start | Tracks/min | First result | Peak RSS |
|---|---:|---:|---:|---:|
| base A / B / C / D | 21 / 13 / 27 / 26 | 10.49 / 10.90 / 7.17 / 11.17 | 18 / 14 / 25 / 14 s | 6.46 / 6.21 / 6.15 / 6.46 GB |
| new (64 GB) B / C / D / E / F / G | 16 / 34 / 8 / 17 / 19 / 21 | 9.98 / 11.37 / 8.56 / 13.04 / 12.23 / 12.39 | 12-16 s | 6.34-6.57 GB |
| new, simulated 8 GB (3 chunks) | 20 / 23 | 3.92 / 4.09 | 20-22 s | **1.91 GB** |
| new, simulated 12 GB (6 chunks) | 12 | 6.95 | 15 s | 3.03 GB |
| new, simulated 16 GB (8 chunks) | 15 | 8.38 | 12 s | 3.63 GB |

On dev the 8 GB simulation runs 3 of 15 cores' worth of model, hence 4 tracks/min; a real 8 GB Mac has 7 model threads, so it gives up about half of its model throughput to stay near 2 GB. Big machines are unchanged (within this box's noise). If Merlin prefers speed on 8 GB, `ANALYSIS_MEMORY_FRACTION` 0.3 gives 4 chunks (~2.3 GB).

### Detail cache from the Rust analysis's own decode

`decode_mono_with` hands every decoded packet (interleaved, before the downmix, plus the leading-silence zeros `measure_detail` adds) to a detail meter thread; the fast pass and whole/now-lane runs store the series with `store_detail`, so the zoom view does not decode the track again. The meter runs beside the analysis (bounded queue of 1024 blocks) and stores when done. Cost: within noise in tracks/min; user CPU +10-20 s per batch (+2-3%).

**Not bit-identical for MP3**: `bench_analysis --check-detail` finds 6 of 12 identical to `measure_detail`: all WAV/FLAC and 2 of 8 MP3s. The decoders differ: the analysis crate decodes with symphonia 0.6, the app with 0.5; on 6 Beatport MP3s 55-77k samples differ (max 0.58). Lengths and column counts match; the gains differ by up to 5 in 2 tracks. The test `the_detail_the_rust_analysis_measures_from_its_decode_is_measure_detail_bit_for_bit` (stereo WAV) passes; the ignored diagnostic `the_app_decode_and_the_analysis_decode_differ_by` prints the per-file sample difference.

### rten 0.24 → 0.27 (branch `q50-rten27`, not on `q50-analysis2`)

Builds without code changes (needs `features = ["fft"]` once beat-this no longer unifies it). beat-this 1.1.0 still pins rten 0.24, so both versions are linked. Logits differ by up to 8.6e-5; stored results differ on 3 of 12 tracks (BPM at 1e-12, beats at 3e-8 s); key, downbeats, waveforms identical. App path: 11.50 / 10.91 tracks/min vs 12.39 between them, user CPU 626-632 s vs 549 s (+14%), sys 56 vs 116 s (half the page faults), peak RSS +0.3 GB. Not worth it: not bit-identical, slower, and no buffer-pool reuse API.

## Render results

Branch `q50-render` (worker q50-render, 2026-10-29). Before = `976c9bf` app and design-system code with this branch's harness, run back to back with the branch on the same box; load average 4-8 on 16 cores (much quieter than the baseline runs, so absolute numbers are lower than above). ### Expand to detail

Trace of the first expand (`FF_PERF_PROFILE=expand FF_PERF_TRACE_OUT=…`): the click task ran the Svelte flush (~76 ms cold, ~40 ms warm) which painted the zoom view **four times** (`setData`, then `setDetailBands`, `setCues` with a fresh array, `setTransport`), then the browser's frame task (~32 ms: layout of the new panel, paint, commit), then the engine's own and the container's `ResizeObserver` repainted once more, and while playing the interpolation loop painted again in the same frame.

Changed (`waveform-display.js`, `WaveformView.svelte`): with `paint: 'frame'` (set by `WaveformView`; harness pages keep the synchronous default) data setters and paused transport reports schedule one paint in the next animation frame; the size observer repaints only when a canvas size changed (the first paint's measured size is kept, so the first observer callback is a no-op), the container observer is gone (the canvases' own observer covers it), and the interpolation loop skips a frame the scheduled paint already drew (that paint advances the clock first). Paint code is untouched, so the pixels are the same (smoke `waveform-detail` checks first draw = settled draw; `player` reads the zoom pixels).

| | Before | After |
|---|---|---|
| expand flush (warm) | 40 ms (paint 27) | 10 ms |
| expand: click task / frame task (cold, first expand) | 76-100 / 31-41 ms | 15 / 84-93 ms |
| expand longest task, first / later expands | 72-97 / 0 ms | 82-93 / 0-66 ms |
| expand to detail drawn (median of 4) | 81-89 ms | 91-99 ms |

**Not reached: no long task over 50 ms.** The total work did not shrink much; it moved. The one cold paint (~60 ms: zoom ring 35, overview 10, forced layout 15, JIT-cold code) now sits in the frame task together with the first layout and raster of the new panel (~30 ms). Getting under 50 ms needs the zoom view drawn one frame after the panel appears (the panel's first frame would show an empty zoom area), a visible change, so left for a decision.

### Rows: sort, search clear, 2k playlist, fling

Profile of a title sort at 10k (57 ms flush, load 8): `sortTracks` 25 ms (17 of it `sortValue` reading through the track proxies), row updates 20 ms (text cells, tag/swatch branches, the `TrackTable` row div), per-row `cellPlan` 4 ms (every row rebuilt its plan because `syncSortIndicators` hands out a new columns array), `persist()` 2 ms. Fling (30 frames, row bands on): ~10 ms of script per frame (text cells, the library's `status`/`rowCover` getters, mini-waveform bitmap blits); the rest of each frame is native layout/raster of the headless software renderer.

Changed: `TrackRow` shares one cell plan per column layout (cached by the columns array, then by a key/width/flex/min/align signature), so a sort or a header indicator change no longer recomputes or re-diffs the cells of every row; sort and clear-sort write the table layout to `localStorage` when idle (`requestIdleCallback`, timeout 1 s, `setTimeout` 200 ms without it, and on `pagehide`) instead of inside the click. `perf10k` takes `FF_PERF_ROW_BANDS=1` (row waveforms, as a real library has) and `FF_PERF_PROFILE=fling`.

Two back-to-back pairs (`ab2`, `ab3`, load 4-6; script ms is the steadier number):

|---|---|---|
| sort title asc, script | 39-42 ms | 31-33 ms |
| sort artist, script | 33-39 ms | 28-42 ms |
| search clear, script | 20-32 ms | 18-21 ms |
| open 2k playlist, script | 37-38 ms | 30-34 ms |

A few ms per click; the rest is outside the design-system rows: `sortTracks`/`sortValue` and the `TrackTable` row wrapper (both off this branch's write list), and the library getters (`status` via `fileStateOf`, `rowCover`) that every visible row reads.
