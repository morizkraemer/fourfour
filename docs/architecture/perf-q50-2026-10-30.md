# Q50 perf baseline (2026-10-30)

Status: harness built and baseline measured on the `dev` box (Linux, 16 cores, no display, no audio device), branch `q50-harness` from `ov-1028`. Nothing is fixed yet; this is step 1 of the Q50 fleet. Earlier work this builds on: `performance-2026-10.md` (Q20 startup, Q23 track load, scroll, search).

**Read every number with the load average next to it.** The box ran at load 42-75 on 16 cores during all runs (other workers building and analysing). CPU-bound numbers (analysis, frontend boot, sorts) move up to about ±40% between runs; structural ones (payload bytes, decode start, cached reads, call counts) do not. Ranges below are min-max over the runs listed under "Runs".

## The command

```bash
scripts/perf.sh          # or: cd app && npm run perf
```

One command, about 12 minutes on a loaded box (first run also generates the 10k library, ~15 min). It prints a table and writes one JSON report to `benchmark/results/q50/perf-<stamp>.json` (gitignored); raw per-step output stays in `~/.cache/q50-perf/raw-<stamp>/`.

| Step | Tool | What it measures |
|---|---|---|
| startup backend | `bench_startup run` (release) | `load_state` on a generated 10k-track library: track query, `build_track_infos`, playlists, JSON. Once after evicting the library's page cache (`posix_fadvise DONTNEED`, no root needed), then 3 warm runs (median). |
| track load backend | `bench_startup load`, `bench_startup audio` | `get_analysis_data` (60 tracks, median/p95); symphonia probe, first packet, seek-to-middle decode on 12 real files; `waveform_detail::detail_bytes` cold (empty cache) and cached. |
| playback engine | `cargo test --release latency_load_and_seek_to_first_audio` | `PlaybackEngine` load and seek to first audible buffer with the fake output backend (existing test). |
| import | `bench_startup import` | 1000 symlinks to real dataset files (992 readable): survey, scan (lofty), `plan_for_library`, commit (exists check + `add_tracks`). Into an empty library with cold and warm page cache, and into the 10k library. |
| analysis | `bench_analysis --profile 3`, then `bench_analysis` | Per-stage ms from `Analysis::ms` (decode, resample, mel, predict = ONNX, fit, mp3, key, waveform/bands) plus `to_app_result` and the library write, one track at a time with all threads; then throughput of 6 tracks through `run_track_analysis` (the app path, staged). |
| frontend | `app/smoke/perf-q50.spec.ts`, `perf10k.spec.ts`, `perf-bulk-analysis.spec.ts` | Production build + smoke Tauri mock at 10k tracks: cold (fresh browser context) and warm (reload) boot to first row and interactive; track load to overview painted and to detail series; expand to detail drawn; import UI from click to rows; steady-state UI (scroll, search, sort, select, playlist, palette); UI while bulk analysis runs. |

Knobs: `FF_PERF_TRACKS`, `FF_PERF_IMPORT`, `FF_PERF_ANALYSIS`, `FF_PERF_PROFILE_TRACKS`, `FF_PERF_SKIP=startup,load,import,analysis,playback,frontend`, `FF_PERF_AUDIO` (dataset root, default the main checkout's `benchmark/datasets`), `FF_PERF_DIR`, `FF_SMOKE_PORT`. Every bench subcommand also prints a `PERF {json}` line, so each step runs alone.

### What the frontend numbers are and are not

- The mock answers in-page (no IPC, no WebKit). Startup passes the 10k payload through `addInitScript`, so its parse lands in boot like the real IPC JSON would, but the cost is Chromium's, not WKWebView's.
- The mock's `get_analysis_data` goes through a Playwright `exposeFunction` round trip and `get_waveform_detail` builds its buffer in the page: both cost ~0.5 s each and are **not app time**. The suite reports them separately and times the app from the moment the mock answers ("after backend answer"). Raw "track load to overview" (550-680 ms) is mostly mock.
- Real backend time for the same commands comes from the Rust rows.

## Worst offenders, ranked per path

Ranked by user-felt time: how long, how often it is hit, and whether it blocks the UI.

### Startup

1. **Frontend boot is one long main-thread block: 0.5-0.9 s longest task, ~0.9-1 s total blocking (cold).** CPU profile of boot at 10k (`FF_PERF_PROFILE=boot`, perf10k "boot profile"): 950 ms `(program)` (native: script parse, payload clone, layout), 540 ms in Svelte's first flush (`flush` → `process_fn`), of which `bind_element_size` effects 156 ms self (an element-size binding reads layout synchronously on mount), `mapTrackInfoToLocal` 71 ms, the search haystack warm-up (`trackHaystack`) 62 ms, `ensureFavoriteSlots` 29 ms; 215 ms GC. Next: split the first flush (rows first, warm-ups after first paint), find which `bind:clientWidth/Height` runs per row or per cell.
2. **Backend `build_track_infos`: 254-637 ms at 10k**, up to 2x with a cold page cache (it reads the PWAV section of 10k ANLZ files). Plus the track query (85-157 ms). Q20 already parallelised it; what is left is the file count. Options: keep the 400-byte preview / row bands in SQLite, or send previews lazily for visible rows.
3. **8.5 MB `load_state` JSON** (64-140 ms to serialise here; WKWebView parse on the Mac unmeasured). Shrinks with item 2's lazy previews.

### Track load

1. **Waveform detail the first time a track opens: 0.8-1.8 s median, up to 2.2 s p95** (`band_analysis::measure_detail`: one full single-threaded decode plus the 3-band meter, then a cache file). Selecting a row prefetches it for that row and the next two, so a double-click on an unselected row pays it in full. It decodes the same file that analysis already decoded and whose bands (`waveform::compute`) analysis already measured at a lower rate. Options: produce the detail series during analysis (same decode), or parallelise the meter.
2. **Expand to detail drawn: 110-149 ms** in the page (`bandsFromDetailBytes` on a 1.44 MB series plus the first zoom draw).
3. Overview painted 47-78 ms after the backend answers; backend answer 3-6 ms; decode start and first audio under 10 ms. **Not an offender**: the audio path is fast.

### Import (1k files)

1. **Scan with a cold page cache: 0.9-1.5 s** (lofty tag reads, one file after the other); warm 0.17-0.25 s. IO-bound; a parallel scan would overlap the reads.
2. **`add_tracks`: 0.43-0.63 s for 992 tracks**, almost all of `commit_import` (the exists check is 14-51 ms). Evidence: the import WAL grew to 25 MB for 992 tracks: the full-size embedded artwork is written as a blob per track inside the transaction. Options: store a downscaled thumbnail, or write artwork after commit.
3. **Plan into a 10k library: 256-366 ms** (`plan_for_library` loads every library track with `get_all_tracks` to build the duplicate index), grows with library size.
4. **UI: one 275-319 ms long task when 1k rows land in a 10k library** (worst frame ~330 ms).

### Analysis

1. **The ONNX beat model (`predict`) is 86-89% of every track** (12-22 s of 14-24 s per 2-minute track with 15 threads at load ~50). Everything else together is ~2 s. Any real throughput win is here: model threading/batching, smaller input (window/hop), or a quantised model; BPM/grid results must stay identical, so this needs a reference comparison.
2. **Staged analysis decodes and resamples every track twice.** `Pass::Fast` and `Pass::Grid` are two separate `analyze_controlled` calls, and each starts with `decode_mono` and a resample (`fourfour-analysis-rs/src/service.rs`, `analyze.rs`): ~1.2-1.6 s of decode + resample per extra pass. Keeping the decoded audio for the grid pass (or one pass that reports waveform/key early) removes it.
3. **Mel + resample + decode: ~1.8-2.6 s per 2-min track**, serial before the model.
4. Library write 52-62 ms and fit 45-57 ms per track: not offenders.

Throughput is 0.9-1.3 tracks/min here for 6 tracks; Q21 measured 2.36/min on 50 tracks with 8 workers on a quieter box (`docs/analysis/app-integration-2026-10.md`). The 6-track run is short on purpose (5-7 minutes); raise `FF_PERF_ANALYSIS` for a steadier figure.

### UI responsiveness

1. **Typing during the bulk fast pass: worst keystroke 0.67-2.4 s, palette up to 1.3 s; the main thread is busy ~0.7 s per second even with no input and no events** (`perf-bulk-analysis.spec.ts`, owned by the bulk-analysis worker). Idle (no analysis) is 0.8 s/s too while scrolling, so part of this is the headless renderer; worth a profile before blaming the app.
2. **Sort at 10k: 141-280 ms per click**; search clear up to 389 ms; opening a 2k playlist 165-302 ms. All are O(N) passes over Svelte-proxied tracks (Q20's remaining items).
3. Fling scroll p95 54-109 ms (row mount + mini-waveform draw).

## Track load results

Branch `q50-trackload` (from `ov-1028`). Target: the first detail waveform of a track.

**Cause.** `measure_detail` is one single-threaded pass: symphonia decode, then the `DetailMeter` (four biquads per sample plus the column extremes). On the 12 harness files at load 24 (release): decode 375-384 ms, meter 295-303 ms. In the app's dev build (`pioneer-test-ui/dev.sh` runs `cargo tauri build --debug`) the meter is unoptimised: `pioneer-usb-writer` had no `profile.dev` opt-level, so the meter took 1,565 ms instead of ~300 (5x), and the whole detail 2.6 s per 2-minute preview. The disk cache (512 MiB LRU in the app data folder, keyed by path, size and mtime) already survives restarts; only the first open of a track pays.

**Changes.**

1. `Cargo.toml`: `[profile.dev.package.pioneer-usb-writer] opt-level = 3` (like the symphonia and analysis crates). Rebuild cost: the writer crate only.
2. `band_analysis::decode_blocks_parallel`: a reader thread splits the packets into segments of 256 packets; up to 6 threads (cores - 1) decode a segment each with a fresh decoder that first decodes the 16 packets before it and drops them (MP3 bit reservoir, overlap-add and synthesis state); the meter consumes the segments in order on the calling thread while later ones decode. Read-ahead is bounded (2 x threads + 2 segments, ~50 MB for a stereo 44.1 kHz track). `measure_detail` uses it; the analysis paths (`decode_blocks`, `measure_waveforms`) are untouched.
3. Row press warms the detail: `createDetailPrefetcher().now(id)` on pointer-down in `TrackTable`, ahead of the 150 ms debounced select prefetch, so a double-click on an unselected row starts the decode 250-400 ms earlier.
4. For the analysis (follow-up, not wired): `band_analysis::measure_waveforms_and_detail` (one decode feeds both meters) and `waveform_detail::store_detail` (writes the cache entry).

**Equivalence.** `bench_startup detail <list>` compares, per file, the parallel decode with the single-threaded one sample by sample (f32 bits) and the detail bytes of old and new `measure_detail`: **identical on 67/67 files** (49 MP3, 12 WAV, 6 FLAC, every 20th file of the dataset list, previews and full tracks) and on the 12 harness files. Unit test: a 40 s WAV through 3 threads gives the same samples, detail and waveforms as one thread.

**Before / after** (back to back on the same box, median/p95):

| Build | Files | Before (one thread) | After | Load |
|---|---|---|---|---|
| release | 12 harness previews | 636 / 673 ms | 351 / 385 ms | 28 → 26 |
| release | 67 mixed (incl. full tracks) | 752 / 4,354 ms | 447 / 2,503 ms | 24 → 33 |
| dev (`dev.sh`), writer unoptimised → optimised | 12 harness previews | 2,622 / 3,312 ms | 456 / 555 ms | 21 → 23 |
| harness `bench_startup audio`, `detail_cold` | 12 | 844-1,820 ms (baseline runs, load 42-75) | 396 / 521 ms | 24 |

Cached reads stay 0.9-2.8 ms. The parallel decode leaves the meter as the floor: after the change the detail takes about the meter's time (~300 ms per 2-minute track, ~0.9 s for a 6-minute one on this box).

**Expand to detail (110-149 ms, 200-330 ms at load 49).** Profile (`FF_PERF_PROFILE=expand npx playwright test perf-q50 --grep expand`): 141 ms in Svelte's flush, of which 85 ms is `WaveformDisplay.setData` → `_paint` (`_renderZoom` 57 ms, `_renderBands`/`drawBandRange` 34 ms); `bandsFromDetailBytes` is already zero-copy. The time is in the design-system renderer (`prototyping/viewport/design-system/waveform-display.js`), outside this branch's scope.

**Follow-ups.**

- Analysis fills the cache: in `analysis_run.rs` swap `measure_waveforms(&bands_path)` for `measure_waveforms_and_detail` and `store_detail` into the app data `waveform-detail` folder; an analysed track then never decodes for its detail (q50-analysis owns that file tonight).
- Meter in parallel (the remaining ~300 ms): needs `DetailMeter` to hand out raw peaks and extremes per segment (`pioneer-usb-writer/src/waveform/detail.rs`); segments start on 2400-column edges, run with an audio pre-roll, and are checked for identical columns on an overlap before they are joined.
- Cache size: 512 MiB holds ~100 six-minute tracks (5 MB each); a larger cap or a compressed file keeps more of a library warm.
- Expand: draw the zoom view once per frame after mount instead of in the mount flush (design system).

## Reproduce one piece

```bash
cargo build --release --bin bench_startup --bin bench_analysis
target/release/bench_startup run ~/.cache/q50-perf/lib10000
target/release/bench_startup audio ~/.cache/q50-perf/audio-load.txt ~/.cache/q50-perf/work
target/release/bench_startup import ~/.cache/q50-perf/import1000 ~/.cache/q50-perf/work [~/.cache/q50-perf/lib10000/library.db]
FOURFOUR_MODELS_DIR=~/.cache/fourfour-models target/release/bench_analysis --list ~/.cache/q50-perf/audio-analysis.txt --limit 6 --profile 3
cd app && FF_PERF_Q50=1 FF_PERF_TRACKS=10000 npx playwright test perf-q50
cd app && FF_PERF_PROFILE=boot FF_PERF_TRACKS=10000 npx playwright test perf10k --grep 'boot profile'
```

## Not measured

- A real Tauri window: IPC transfer, WKWebView parse and paint, macOS. Mac numbers need the app.
- Audio output; the engine latency uses the fake backend.
- Cold start of the Rust process itself (Tauri init, model load is 0.2-0.3 s).
- BPM/grid/key results: this step changes no algorithm, so nothing to compare yet. Fix branches must diff results against a reference run (`bench_analysis` output or `benchmark/`).
