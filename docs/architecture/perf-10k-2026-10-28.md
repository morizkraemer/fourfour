# Performance at 10,000 tracks (2026-10-28, O4)

Branch `ov-perf` (from `ov-1028`). Measured on the shared `dev` box (Linux, no display) while its load average was 26-40 on 16 cores, so wall-clock browser numbers carry roughly +-30% noise. Where that matters, the comparison below uses CPU time (`process.cpuUsage`, Chromium `ScriptDuration`) and medians of three runs.

Earlier passes (Q20, Q23, Q28 in `performance-2026-10.md`) already fixed row virtualisation, `build_track_infos`, analysis payloads and the first search keystroke. This pass re-measured everything at 10k with the smoke mock and found the remaining cost mostly on the Rust side.

## Method

**Browser** (`app/smoke/perf10k.spec.ts`, opt-in): `FF_PERF_TRACKS=10000 npx playwright test perf10k`. The smoke fixture (`fixture.ts`) generates N tracks and a 2,000-track playlist when `FF_PERF_TRACKS` is set; the normal smoke stays at 20 tracks. Measures boot, scroll and fling frame times, search keystrokes, sort, select to inspector, opening the 2k playlist, palette open and filter. `FF_PERF_OUT=<file>` writes JSON; `FF_PERF_PROFILE="<step name>"` (or `boot`) prints a CPU profile of that step from an unminified build. Per step it records wall time to the second `requestAnimationFrame`, long-task time and the CDP `ScriptDuration` / layout / style / task deltas.

**Store hot paths** (`app/src/stores/perf-10k.test.ts`, opt-in): `FF_PERF_TRACKS=10000 npx vitest run src/stores/perf-10k.test.ts --reporter=verbose`. Runs `filterTracks`, `sortTracks` and `tracksForSidebarSource` on 10k reactive tracks and reports CPU ms (median of 7 and first run).

**Rust** (`bench_startup`, release): `save <dir> <tracks>` times `replace_playlists` (what `save_state` runs) on 10k tracks and 12,000 playlist rows (20 playlists of 500 plus one of 2,000); `scan <dir> <files>` writes N tiny generated MP3s (ID3 tags and four silent frames, in the given dir, not `benchmark/data`), times `scanner::scan_directory`, then the insert loop the `scan_directory` command used (one `track_exists_by_path` + `add_track` per track) against one transaction (`add_tracks`). `run` is the existing `load_state` breakdown.

```bash
cargo build --release --bin bench_startup
target/release/bench_startup save ~/.cache/ov-perf/save 10000
target/release/bench_startup scan ~/.cache/ov-perf/scan 10000
target/release/bench_startup run ~/.cache/q20-bench/lib10000
cd app && FF_PERF_TRACKS=10000 FF_PERF_OUT=/tmp/perf.json npx playwright test perf10k
```

## Fixes

1. **Scan/import inserted one track per transaction.** `scan_directory` and `scan_files` ran `add_track` per file in autocommit mode: one WAL commit per track, 1.5 ms each. Both commands now share `add_scanned_tracks` (`pioneer-test-ui/src/main.rs`): skip known and repeated paths, then one `add_tracks` transaction. 15.6 s to 0.52 s for 10k files. A failure now rolls the whole batch back instead of leaving a partial import.
2. **`save_state` rewrote every playlist row on every edit.** `replace_playlists` deleted and re-inserted all `playlist_tracks` rows (12k here) with an unprepared INSERT each, for any rename, reorder or add, on the main thread while holding the library mutex. It now compares the stored track list per playlist and rewrites only the ones that changed, and uses a cached prepared statement. Test: `replace_playlists_applies_reorders_removals_and_repeat_saves`.
3. **Table derivations went through reactive proxies.**
   - `sortTracks` computed the sort key (regex, `toLowerCase`) inside the comparator, twice per comparison; it now computes it once per track.
   - Opening a playlist built a 10k-entry `Map` through proxies on every recompute; it now uses an id-to-index map cached per library array and reads only the playlist's own tracks.
   - `filterTracks` iterated the proxy array for every keystroke; it now matches on plain search text by index, narrows from the previous result when the new terms extend the old ones, returns the source array unchanged when everything matches, and touches proxies only for the matches. Tests added in `search-cache.test.ts`.

No visual or styling changes, no new dependencies, no schema change.

## What the profiles say is left

- Browser time at 10k is now mostly Svelte's derived-chain flush plus layout/paint of ~42 rows; a sort click is ~55-85 ms of script and ~100 ms on screen under this box's load. Nothing in the app code stands out above ~10 ms self time.
- `library.tracks = [...library.tracks]` in `bumpLibraryTracks` copies 10k proxies; it only runs when an analysis changes a row's bpm/key.
- `load_state` is 370-500 ms warm and 2.9 s cold at 10k, dominated by reading each track's ANLZ preview; already parallel (Q20).
- The scan's remaining cost at 10k is tag parsing (1.4 s for tiny files; real audio files are slower and unmeasured). `track_exists_by_path` is still one query per file (indexed, about 10 us).
- Not measured: a real Tauri window (WebKit, IPC), real audio files for scan, cold-disk save.
