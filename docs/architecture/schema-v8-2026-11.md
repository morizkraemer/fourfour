# Library schema v8 (2026-11, `r81-schema-bump`)

Branch `r81-schema-bump` from `ov-1028`, parked for Merlin (STATE "Waiting on Merlin" 31: library DB schema changes need his say). This is the app's own `library.db` (`pioneer-library`), not the Pioneer USB export format; nothing in `pioneer-usb-writer` or the sync engine changes.

One bump, three changes, all found in the 50k runs (R13 in `perf-run-2026-11.md`, robustness in `robustness-2026-11.md`):

1. **Folded artist/title keys stored on the track.** The duplicate plan of the first import of a session folded artist and title (Unicode NFKD) for the whole library: 0.9-1.5 s at 50k. R33 keeps the index in memory between imports; the first build still folded everything.
2. **Covers out of `library.db`** into a content-addressed store next to it. At 50k the db was 7.5 GB, 5x everything else in it, and the import commit swung 65 ms to 4.7 s.
3. **Analysis failures in the db** instead of `analysis-failures.json` in the app data folder. The side file is keyed by track id but lives outside the library, so a library switch or restore points it at other tracks; the db row goes with the track (cascade) and with the backup.

## Schema diff (v7 -> v8)

```sql
-- 1. folded keys (normalise_tag of artist and title; '' when empty)
ALTER TABLE tracks ADD COLUMN artist_key TEXT NOT NULL DEFAULT '';
ALTER TABLE tracks ADD COLUMN title_key  TEXT NOT NULL DEFAULT '';
CREATE TABLE library_meta (name TEXT PRIMARY KEY, value TEXT NOT NULL);   -- 'tag_fold' = fold version

-- 2. covers: the blob table is set aside, the new table holds only the reference
ALTER TABLE artwork RENAME TO artwork_v7_blobs;           -- emptied by the cover move, then dropped
CREATE TABLE artwork (
    track_id   INTEGER PRIMARY KEY REFERENCES tracks(id) ON DELETE CASCADE,
    cover_hash TEXT                                         -- NULL = still in artwork_v7_blobs
);
CREATE INDEX idx_artwork_hash ON artwork(cover_hash);
-- idx_artwork_track (v7's covering index over the blob table) is dropped with the blobs

-- 3. analysis failures
CREATE TABLE analysis_failures (
    track_id         INTEGER PRIMARY KEY REFERENCES tracks(id) ON DELETE CASCADE,
    source_path      TEXT    NOT NULL,     -- the file that failed
    file_size        INTEGER,              -- fingerprint: a changed file is retried
    modified_ms      INTEGER,
    kind             TEXT    NOT NULL,     -- error kind (decode_failed, not_found, ...)
    attempts         INTEGER NOT NULL,
    analyzer_version TEXT    NOT NULL,     -- fourfour_analysis::service::analysis_key
    failed_at_ms     INTEGER NOT NULL
);
```

Cover store: `<library folder>/covers/<first 2 hex>/<sha256 hex>`, one file per distinct image (tracks of one album share a file). SHA-256 is a small std-only implementation in `cover_store.rs` (no new dependency; `sha2` is in `Cargo.lock` through Tauri and could replace it). Files are written to a temp name, synced and renamed, before the row that points at them commits; a crash leaves at most an unreferenced file, which the sweep removes.

## Migration

`schema::initialize` at open, one transaction (`migrate_v7_to_v8`):

1. Add the two key columns and fill them for every track (fold in Rust, one `UPDATE` per track).
2. Rename `artwork` to `artwork_v7_blobs`, create the new `artwork`, insert one row with `cover_hash NULL` per old cover (read through the old covering index, so no blob page is read), drop `idx_artwork_track`.
3. Create `analysis_failures` and `library_meta`, store the fold version, set the version to 8.

All of it commits or none of it does; the blobs are not touched by it, so the open stays fast (no cover I/O). `has_artwork` keeps reading the `artwork` table, so the list shows the same covers before and after.

**Cover move** (`LocalLibrary::move_legacy_covers`), after open, in the app's cover-fill thread, in batches of 32 under the library lock (the lock is let go between batches):

1. Space check first: the bytes left in `artwork_v7_blobs` (`SUM(length(image_data))`, read from the record headers) plus 256 MB must be free on the library's volume (`statvfs`). If not, it stops with `LibraryFailure::DiskFull` and the covers stay in the db, where they are still read; the next launch tries again.
2. Per batch: write each image to the store (skipped when the file is there already), then one transaction sets `cover_hash` (`WHERE cover_hash IS NULL`, so a cover set by hand meanwhile wins) and deletes the moved blob rows.
3. When the blob table is empty: drop it, `VACUUM` (the free pages of the old covers go back to the disk), sweep unreferenced cover files.

Interrupted at any point (quit, crash, full disk): the rows not yet moved are still in `artwork_v7_blobs` with `cover_hash NULL`, are still read from there, and the next run continues with them. Files written by a batch that did not commit are found again by hash.

Fold version: `library_meta.tag_fold` names the version of `normalise_tag` the keys were made with. If a later build changes the fold it bumps `TAG_FOLD_VERSION` and the keys are refilled at open (no schema bump).

## Rollback

There is no downgrade. An older build opening a v8 library sees version 8 > 7 and refuses with `LibraryFailure::NewerVersion` ("saved by a newer version of the app"); it writes nothing (the r51 fixture test `fixture_from_a_newer_schema_is_refused_with_a_typed_error_and_left_alone` covers this path). Going back to v7 means restoring a backup made with the older build, or keeping the old app. The cover store is next to the db, so a v8 backup includes `covers/` and a restore puts it back.

## What callers change

- `pioneer-library`: `set_artwork`, `get_artwork`, `remove_artwork`, `add_track(s)`, `store_pending_artwork`, USB import, Rekordbox import and export read and write through the cover store; removing tracks or replacing a cover deletes files no other track references. Track inserts and updates write the folded keys; `DuplicateCandidate` carries them (`artist_key`, `title_key`) and the index uses them instead of folding. Backup writes and restores `covers/`.
- `pioneer-test-ui`: `FailureMemo` keeps its rules (skip after two failures on an unchanged file, explicit requests run anyway, a success clears the entry) and now reads and writes `analysis_failures` through the library; an entry from another analyzer version counts as none, so a new analyzer retries every failed track. The old `analysis-failures.json` is adopted once (entries whose track still points at the same file) and removed. The cover-fill thread runs the cover move first. Reset removes `covers/` with `anlz/`.
- App (`app/src`): nothing. `get_track_artwork` and the other commands return the same payloads.

## Measured (2026-11-03, Linux `dev` box, load 14-25 from other workers)

Release `bench_startup` built from `ov-1028` (before) and from this branch (after), on the R13 fixtures (`~/.cache/ff-fixture/10k`, `50k`). Import sample: 1,000 mp3 hard-linked from the 25k fixture (885 with covers; all 1,000 are tag duplicates of the 50k library). "After" imports into a v8 copy of the fixture with the covers moved out (made with the new `bench_startup migrate`). Each run is a fresh copy of the base db, synced before the run.

**Migration** (`bench_startup migrate <copy of library.db>`):

| | 10k | 50k |
|---|---:|---:|
| open = v7 -> v8 migration (keys, artwork rename, failure table) | 0.34 s | 3.5 s (load 25, npm builds running) |
| cover move, in the background (8,132 / 40,722 blobs) | 31 s | 240 s |
| `library.db` | 1.54 GB -> 11.8 MB | 7.51 GB -> 59 MB |
| cover files | 106 | 106 |

The fixture has only 120 distinct cover images (the generator's pool), so the store holds 106 files; a real library has about one per album. The move is bound by reading the blobs, hashing (std-only SHA-256) and one commit per 32 covers; the library lock is let go between batches.

**Import of 1,000 files, first import of the session** (ms; 10k: 7 pairs, 50k: 2 pairs)

| Step | 10k before | 10k after | 50k before | 50k after |
|---|---:|---:|---:|---:|
| duplicate plan (builds the index) | 99-135 | 95-255 | 650-696 | 433-533 |
| commit (rows) | 70-103 | 75-169 | 166 / 6,103 * | 177-195 |
| covers in the background (885) | 806-1,300 | 2,240-2,810 | 807-875 | 2,330-2,390 |

\* the before-commit at 50k swings with the writeback of the 7.5 GB db copy the bench makes first (R13 saw the same, 65 ms to 4.7 s); the after copy is 59 MB.

Read: at 50k the first plan is about 30% faster (the NFKD fold of artist and title is gone; path and file-name keys are still folded, NFC + lowercase, and the read of 50k rows stays). At 10k the difference is inside the noise of this box. The commit no longer depends on a multi-GB file. **Covers got slower to store**: each new cover file is written, `fsync`ed and renamed before its row commits (about 1.5 s more for 885 covers here); the blob path wrote them through the WAL with `synchronous=NORMAL`. This is background work after the rows are on screen, but a 10k import's covers would take about 2.5x as long on this box (Mac SSDs `fsync` faster; not measured there).

## Left open

- Cover writes: drop the per-file `fsync` (and guard reads by size), or batch it, if the background fill time matters more than a cover surviving a power cut.
- Path and file-name keys are still folded at the first plan; storing them too would take the rest of the fold out (not asked for here).
- `sha2` (in `Cargo.lock` through Tauri) would hash faster than the std-only SHA-256 (not measured); it is a new direct dependency, so not used.
- A restored v7 backup moves its covers at the next launch (the restore path does not start the cover fill).
- No UI shows or clears the skipped analysis failures (as before); "analyze again" on a track runs it and a success clears its record.
