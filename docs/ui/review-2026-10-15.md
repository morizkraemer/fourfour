# fourfour UX review: organize sidebar, USB sync, layouts, player, end-to-end flow

Method: docs and code read, then the app run in a browser against enriched mocks (30 tracks, 6 playlists, 2 USB volumes, 4 unanalyzed tracks) and driven with Playwright at 1440x900 and 1280x800. 41 screenshots were taken (published with the review page; not in the repo) (`NN-name.png`, referenced as [NN]). The mock enrichment was temporary and has been reverted; nothing was committed.

Not reachable from the browser, reviewed from code only: real sync progress and errors (the Rust command is synchronous and emits only a final report), actual eject/wipe results, real audio and playback, and macOS native behaviour. The native `confirm()` dialogs cannot be screenshotted; their text was captured from the console.

## Overall verdict

The core idea is right and already good. A calm single workspace, a persistent right-side destination you drag into, and a waveform-first player are a real improvement over Rekordbox's modal, tab-heavy workflow. The organize drawer works: drag from library to the docked playlist shows a drop line and a ghost, the sidebar count updates, drop-at-index works [12][13], and the inspector/drawer layering is tidy. The player strip and expanded player are simple and fast. The Escape toggle, the BPM/KEY nudge and the grid Set/nudge are the right small tools.

The problems are not in the organize concept but at its edges. First, **the USB half of the product is the weakest part and does not live up to the vision doc**. Sync, wipe and eject exist only in a right-click menu and use native `confirm()` dialogs. "Sync" always means mirror the whole library, and no screen tells you that. There is no progress, no result, no capacity, no diff and no error surface. The drag-to-USB gesture silently starts a full-library sync, and a docked USB target shows an empty table [32]. Second, there are several small state-visibility gaps (unanalyzed tracks silently skipped, a stale inspector, a picker that hides playlists). Everything else is polish. There is no conceptual problem with the organize panel, the player, or the layouts; there is one with sync.

## What works and should be kept

- Persistent right rail and drawer as a sticky destination, independent of left navigation. Dragging into it is fast and legible [12][13].
- Drop line and drag ghost with the "Artist — Title" label [12].
- New playlist auto-docks and goes straight into inline rename [07].
- Inspector yields to the drawer and returns on collapse [18]. The filled rail with covers is a nice glance (code; covers are empty in the mock).
- Magnetic snap to full width gives a proper "arrange this playlist" mode [16].
- Compact player with a real waveform; the expanded player keeps the library visible above it [04].
- Keyboard model: Space, 1-9 favorites, Esc collapses the expanded player, Cmd+F.
- The visual language is consistent and dark/quiet. Key colouring in the table is useful.

## Per-area review

### 1. Organize sidebar (panel, rail, picker, dock, drop)
- **What it is:** a right-edge rail that pulls out into a destination picker, then hosts one docked playlist or USB as a drop target.
- **Verdict: keep.** Polish only (see list).
- **Why:** it matches the real task, which is to listen on the left and file on the right. It avoids the Rekordbox split-view trap. Persistence of the target across restarts is a real plus.
- **Friction:**
  - The picker is bottom-anchored with a large empty block above it [06][07][09].
  - The picker shows only recents when any exist, so after one use you see a single playlist plus a search box [09]. The fallback to "first four playlists" only applies with zero recents. Playlists beyond the recents are discoverable only by typing.
  - The default drawer width clips the columns that matter for set building. BPM and KEY are cut off at the right edge, and ALBUM is shown instead [13]. The organize layout defaults (#, cover, title, album, bpm, key) assume more width than the drawer has.
  - The drawer overlays the library, so the library's own BPM/KEY/TIME columns are covered [06][13]. You compare keys on the left and the right never at the same time.
  - The rail is very low-contrast [01]. It is the only entry to the feature, and the discoverability bet of the design rests on it.
  - At full width the library is hidden, so you cannot drag from it [16]. This is intentional ("arrange" mode), but nothing tells you that dragging now only works from the sidebar.
  - Dropping onto the sidebar playlist rows still works [14][15], so there are two drop paths with no hint which is preferred.
- **Alternatives:**
  1. Make the picker top-anchored and always list the 4 most-used playlists plus search; keep the recents as an ordering rule only.
  2. Default the organize table to title, bpm, key (+ cover), and let width add album/artist. Mirror the left table's BPM/KEY styling so keys can be compared across panes.
  3. Give the rail a visible label or tab ("Organize") and a slightly lighter surface; show the target name vertically when docked.

### 2. USB sync flow
- **What it is:** choose a stick in the sidebar (or dock it in the drawer), then sync, wipe or eject.
- **Verdict: rethink.** This is the one real problem area.
- **Why:**
  - Sync, wipe and eject are reachable only through a right-click menu on a sidebar row [20] (`menus/context-menus.ts`). The vision doc's own rule says anything only in a context menu must be redesigned. There is no Sync button anywhere.
  - Confirmation is a native `confirm()`: "Sync all playlists to SanDisk 64GB?" and "⚠ Wipe all Pioneer library contents ... This cannot be undone." It is ugly, it blocks the window, it cannot show consequences, and the mock app cannot even screenshot it.
  - Progress is a 11px text in the status bar, "Syncing tracks to USB…", with a spinner and no bar [22]. The result is discarded: the code listens for `write-complete` but throws away the report and just sets "Ready" (`library.svelte.ts`, `listenToWriteComplete`). The added/updated/removed counts are computed by Rust and never shown.
  - Clicking a stick shows its tracks in the same table as the library [19], with no header saying this is the stick's contents, no capacity bar, no "last synced", and no diff against your library. The inspector still shows the previously selected library track while the table shows USB tracks [19].
  - Errors: a failure is `console.error` plus the status text resetting to "Ready". The user is never told it failed.
  - Docking a USB in the drawer shows an empty table with the wrong empty-state text ("Select a playlist or import music") [32], because stick contents are only loaded when the stick is also the selected sidebar row.
  - Sidebar dot: the dot is green only for the *selected* stick and grey for any other mounted stick [19][22]. The vision doc says green means mounted, grey means ejected. In code, ejected sticks vanish entirely, so the "persistent USB you can queue changes for" concept is not implemented.
  - The drawer drop gesture (drag tracks onto a docked USB) triggers a full-library sync. The dragged ids are only logged (`exportTracksToVolume`). The gesture therefore promises a per-track copy and performs something far larger.
- **What a DJ wants:** pick a stick, see what is on it and how full it is, see exactly what will change (add/remove/keep), press one clearly labelled Sync, watch real progress, get a result they can trust ("22 added, 1 removed, 11 unchanged, safe to eject"), then eject. Lexicon and Engine DJ are better at the "plan before you write" part; Rekordbox is no benchmark here.
- **Alternatives:**
  1. **USB as a target panel with a sync footer.** When a USB is docked (or selected), the panel header shows name, capacity bar, and a primary Sync button. Before pressing it, a one-line plan appears: "+22 tracks, -1 track, 11 unchanged, 3.1 GB". Progress replaces the footer; the result stays until dismissed with an Eject button next to it. This matches the vision doc's "USB is a playlist with sync chrome".
  2. **Sync scope = playlists, not library.** Let the user pick which playlists go to the stick (checkbox list in the USB panel), and sync only the tracks they contain. This also fixes the drag-to-USB mismatch: dropping a playlist or tracks adds them to the stick's list.
  3. **Replace `confirm()` with the app's own Dialog** that states consequences ("This removes 1 track from the stick that is not in your library: Old Rekordbox Edit") with a destructive button style. Use the same Dialog for wipe.

### 3. Split-screen and multi-pane layouts
- **What it is:** library + inspector + drawer, all inside one main area, with the player below.
- **Verdict: keep, with polish.**
- **Why:** one set of nested layers (browse, inspector, drawer) with a clear priority order is easy to learn, and it replaced a dual-pane split that nobody found.
- **Friction:**
  - At 1440 the inspector (278px) squeezes the library so that KEY and TIME are cut off at the right edge with no horizontal scroll [02][03]. At 1280 it hides everything after LABEL [37]. The table should reflow or drop low-priority columns as the inspector opens.
  - At 1280x800 with the expanded player and the drawer open, the library area is about 450px high and the drawer is wider than the viewport, because the width saved from a previous full-width session is not clamped [41].
  - There is no way to see the library and a docked target with the same columns visible at the same time [13].
- **Alternatives:**
  1. Auto-hide or reorder table columns by priority (title, bpm, key, time first) when the available width drops.
  2. Clamp the persisted drawer width to the current viewport on load and on window resize.
  3. When the drawer is open, shrink the library instead of overlaying it (the inspector already does this), so columns stay visible.

### 4. Player strip and expanded player
- **What it is:** a full-width compact waveform strip that grows to about a third of the window with an overview plus zoomed Rekordbox-style waveform.
- **Verdict: keep.**
- **Why:** the zoomed waveform with the beat grid [04] is a clear, honest prep tool. Transport is minimal. Esc toggles it. Cue-preview on hold is right.
- **Friction:**
  - The expanded player at 900px high takes about a third of the screen and leaves 18 library rows [04]; at 1280x800 it leaves only about 450px for everything above [41].
  - Cue management is not in the expanded player. Hot cues live only in the inspector (read-only chips and a "+"). The expanded player has no cue markers list, no half/double grid, and no visible dirty/saved state for grid edits. The vision doc and components checklist list these as undecided design work, so this is a known gap rather than a regression.
  - The compact strip and expanded player both show a placeholder cover block with nothing in it for tracks without artwork [03].
  - The inspector's waveform and the player's waveform show the same track twice [03]. They are redundant in the browse state.
- **Alternatives:**
  1. In the expanded player, add cue chips along the waveform (add / delete / jump) and show a small "unsaved" indicator on grid changes.
  2. Let the expanded player height be user-draggable with a minimum; remember it.
  3. Drop the waveform thumbnail from the inspector when the player already shows that track, and use the space for tags/cues/notes.

### 5. Detail pane (inspector)
- **What it is:** right pane with artwork, a waveform thumbnail, metadata, hot cues and the file path.
- **Verdict: keep, fix the placeholders.**
- **Friction:**
  - "ADDED" is a hardcoded "2 days ago" for every track (`Detail.svelte`). In multi-select, TOTAL DURATION, BPM RANGE and KEYS are all "—". These are fake or empty and erode trust in the pane.
  - In a USB view the inspector shows the last selected library track [19].
  - Nothing in the pane says whether a track is analyzed or will be included on the stick.
- **Alternatives:**
  1. Show real date added and fill the multi-select summary (BPM range, key set, total time); that is what you want when building a set.
  2. Add a "On stick: SanDisk (yes/no)" and "Analysis: ok/needed" line.
  3. Clear or retarget the inspector when the left view switches to a USB.

### 6. End-to-end flow (new user to gig)
Walkthrough, with step counts for a DJ with a folder of music and one stick:

| Step | What happens | Verdict |
|---|---|---|
| Scan/import | Cmd+O or drop files; a dialog asks "Analyze imported tracks?" | Fine. One extra click that nearly always answers yes. |
| Analyze | Status bar shows progress; rows show "—" for BPM/key until done | Works, but unanalyzed rows look the same as analyzed ones except for dashes [35]. |
| Organize | New playlist, drag in, order by drop position | Good [07][12][13]. |
| Sync | Right-click stick, Sync to USB, confirm | Hard to find; no plan, progress or result. |
| Check | Click the stick to see what it holds [19] | Possible, but no diff against the library. |
| Eject | Right-click, Eject, confirm | Hard to find. |

**Biggest gap: the DJ never learns that unanalyzed tracks are skipped.** The writer only includes tracks that have analysis (`get_analyzed_tracks`). If you import 200 tracks, tell the app "Not now" to analysis, and sync, those 200 are missing from the stick and from its playlists. The report shows no counts for skipped tracks, and a playlist that mixes analyzed and unanalyzed tracks arrives shorter than on screen. Nothing warns you.

## Sync model (from the code)

What actually happens when the user chooses "Sync to USB" or drops onto a docked USB:

1. **One-way, library to stick.** The stick is never read back into the library, except for the read-only view of what is on it. There is an `import_from_usb` function in the library crate, but no UI calls it.
2. **Scope is the entire library, not the playlists.** `LocalLibrary::sync_usb` takes every analyzed track (`get_analyzed_tracks`) and copies all of them, whether or not they are in any playlist. A 20,000-track library will try to fill the stick; there is no capacity check before the copy, so a full stick fails mid-run.
3. **Unanalyzed tracks are silently excluded** from the copy and from playlist contents (see above).
4. **Incremental.** Per track: new tracks are added, changed files are replaced, metadata changes rewrite analysis files only, and unchanged tracks are skipped. IDs on the stick are kept stable.
5. **Deletes.** Any track on the stick that is not in the library's analyzed set is removed from the stick, including the audio file, its ANLZ analysis folder and artwork. This means anything the user put on the stick another way (for example from Rekordbox, or an unanalyzed track) disappears on the next sync, without a warning that names it. The only warning is the generic "Sync all playlists" text.
6. **Playlists are recreated.** Before writing, the app deletes every playlist in the library database and recreates all of them from the front-end state (`sync_playlists_to_library`), then both Pioneer databases (`export.pdb` and OneLibrary) are rebuilt from scratch. The favorites slots ("Favorites 1..9") are ordinary playlists and are pushed to the stick too. Playlists on the stick that are not in the library are dropped.
7. **Wipe** removes only `PIONEER/` and `Contents/`; other files on the stick are left alone. It has no undo.
8. **Execution.** `write_usb` is a synchronous command that holds the library lock for the whole run. There is no progress event, only one final `write-complete` event with five counts, and the UI ignores the counts. Whether the window stays responsive during a long copy needs to be checked on a real stick.
9. **Volume list.** On macOS it lists everything under `/Volumes` and on Linux everything under `/media` and `/mnt`; there is no removable-drive filter, so the system disk can appear as a "USB device" and offer Eject/Wipe.

**Does it match a DJ's mental model?** Partly. "Mirror my library to the stick" is a coherent model, but it is not the one the UI suggests. The confirm text says "Sync all playlists", the organize drag implies "copy these tracks", and the docs describe USBs as "persistent playlists". A DJ expects the stick to contain *the sets they prepared*, not the whole library, and expects to be told before anything is deleted. The reliable fix is to make the scope explicit (chosen playlists), show the plan, and say what will be removed by name.

## Open questions for Merlin

1. Should sync scope be "chosen playlists" (recommended), "whole library", or both with a toggle? This decides the drag-to-USB behaviour.
2. Should unanalyzed tracks block sync, be analyzed automatically at sync time, or be skipped with a visible warning?
3. Do you still want USBs that persist when ejected (queue changes, sync on next mount), as in `vision.md`? The code today only lists mounted drives, so this is a build decision, not polish.
4. Is anything on the stick that fourfour did not put there allowed to be deleted? If not, sync should only touch files it owns.
5. Where should cues be edited: the expanded player (recommended) or the inspector?
6. Should the favorites slots (Favorites 1..9) go to the stick as playlists? They do now.
7. Is `import_from_usb` (stick back into library) wanted in the UI?
